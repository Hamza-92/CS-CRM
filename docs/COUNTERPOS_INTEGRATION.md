# CounterPOS integration foundation

The CRM remains the source of truth for customers, subscriptions, renewals, and payments. CounterPOS remains the source of truth for tenant domains, encrypted database credentials, schema state, and execution of tenant operations.

## Record linkage

`application_instances.counterpos_tenant_id` stores the UUID of the matching CounterPOS control-plane tenant. The column is nullable and unique, so existing CRM records are not changed and one CounterPOS tenant cannot be assigned to multiple CRM instances.

The CRM caches non-sensitive operational state on the application instance:

- `counterpos_status`
- `counterpos_schema_version`
- `provisioning_template_code`
- `provisioning_template_version`
- `last_synced_at`

CounterPOS remains authoritative for these values. They will be refreshed through the integration service added in the API phase.

## Operation tracking

Every requested tenant action is represented by a `tenant_operations` record. Supported initial types are provisioning, connection testing, migration, template seeding, activation, pausing, retirement, and synchronization.

`idempotency_key` is generated by the CRM and sent to CounterPOS as the shared external reference. `counterpos_operation_id` stores the UUID returned by CounterPOS. Status progresses from `queued` to `running`, then to `succeeded`, `failed`, or `cancelled`.

`request_payload` must contain only non-sensitive choices such as a template code or migration target. Database passwords, API secrets, raw SQL, and decrypted CounterPOS credentials must never be written to this table.

## Local migration

```bash
php artisan migrate
```

Both schema changes are additive. Existing customers and application instances retain their current values, with all new linkage fields initially null.
